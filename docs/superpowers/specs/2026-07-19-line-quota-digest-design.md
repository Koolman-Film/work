# ลดข้อความ LINE ให้อยู่ใต้โควตา 300/เดือน — Design

**Date:** 2026-07-19
**Status:** Approved (design), pending implementation
**Author:** brainstormed with Claude

## Summary

โควตา LINE เต็ม 300/300 การแจ้งเตือนทุกอย่างจึงเงียบตั้งแต่นั้น งานนี้ลด
ปริมาณข้อความจาก ~464/เดือน เหลือ ~231/เดือน (77% ของโควตา) ด้วย 3 อย่าง:

1. **รวมการแจ้งแอดมินเป็น digest วันละครั้ง 09:30** แทนการยิงทุกเหตุการณ์
2. **เลิก push สลิปเงินเดือนเข้า LINE**
3. **ใส่ตัวกันโควตาหมด** ไม่ให้ระบบเงียบหายโดยไม่มีใครรู้อีก

ไม่มี schema migration ไม่แตะสูตรเงินเดือน

## Context

### ตัวเลขจริงจากระบบ (ตาราง `Notification`)

| เดือน | admin fan-out | แจ้งพนักงาน | สลิป | รวม |
|---|---|---|---|---|
| ก.ค. 2569 | **300 (65%)** | 129 | 35 | **464** ← ตัน |
| มิ.ย. 2569 | 95 | 165 | 4 | 264 |

**ผู้รับ:** แอดมินผูก LINE **3 คน** · พนักงานผูก LINE **48 คน**
**เหตุการณ์:** ก.ค. ใบลา 33 + เบิก 40 · มิ.ย. ใบลา 54 + เบิก 68

### ต้นตอ

มิ.ย. ใช้ 264 ทั้งที่มีเหตุการณ์ *มากกว่า* ก.ค. เพราะ มิ.ย. มีแอดมินผูก LINE
~1 คน แต่ ก.ค. มี 3 คน — ยืนยันจากอัตราส่วน `117 ข้อความ ÷ 40 คำขอ = 2.9`

**admin fan-out เป็นที่เดียวในระบบที่หนึ่งเหตุการณ์กินโควตาหลายใบ** ส่วน
การแจ้งพนักงานเป็น 1:1 อยู่แล้ว digest จึงช่วยฝั่งแอดมินมหาศาลแต่แทบไม่ช่วย
ฝั่งพนักงาน (48 คน รับเฉลี่ย 3.4 ครั้ง/เดือน กระจายทั้งเดือน)

**ปัญหาโตตามจำนวนแอดมิน ไม่ใช่จำนวนพนักงาน** — เพิ่มแอดมินเป็น 6 คนวันนี้
= 122 เหตุการณ์ × 6 = **732 ข้อความ/เดือน** ทั้งที่พนักงานเท่าเดิม

## Decision

### 1. Digest แอดมินวันละครั้ง 09:30 — รายงาน "สถานะ" ไม่ใช่ "เหตุการณ์"

Cron `TZ=Asia/Bangkok 30 9 * * *` ถามว่า **ตอนนี้ค้างอะไรอยู่** แล้วส่งสรุป
ให้แอดมินแต่ละคน — ไม่ใช่การสะสมว่าเมื่อวานมีอะไรเข้ามา

เหตุผลที่เลือกแบบ "สถานะ": ไม่ต้องเก็บ state ระหว่างวัน, แม่นยำเสมอ, และถ้า
แอดมินเคลียร์งานไปแล้วตอนกลางคืน จะไม่ถูกเตือนซ้ำ — ซึ่งการสะสม event ทำไม่ได้

ใช้ `loadSidebarBadgeCounts(assignments)` ที่มีอยู่แล้ว — มันนับใบลา/เบิก/
ต้องตรวจสอบ **แยกตามสาขาที่แอดมินคนนั้นดูแล** อยู่แล้ว

**ไม่ส่งเมื่อไม่มีของค้าง** — วันที่ยอดรวมเป็น 0 ข้ามไปเลย

### 2. เลิก push สลิปเงินเดือน (48 ข้อความ/เดือน)

พนักงานเปิดดูสลิปจาก rich menu ได้อยู่แล้ว การ push บอกว่า "สลิปออกแล้ว"
เดือนละครั้งคือของที่แพงที่สุดต่อประโยชน์ที่ได้ในระบบนี้

**Trade-off ที่ยอมรับ:** พนักงานจะไม่ได้รับแจ้งเมื่อสลิปออก ต้องเข้าไปดูเอง
ต่างจากใบลา/เบิกตรงที่รอบจ่ายเงินเดือนมีกำหนดแน่นอนอยู่แล้ว จึงคาดเดาได้
ย้อนกลับได้ด้วยการเรียก `notifyPublishedSlips` กลับมาบรรทัดเดียว

### 3. ตัวกันโควตาหมด

ก่อน push ทุกครั้ง เช็คโควตาคงเหลือ ถ้าต่ำกว่าที่กันไว้:
- **ไม่ push** และบันทึก Notification ว่าถูกข้ามพร้อมเหตุผล
- **แจ้งแอดมินทางกระดิ่งในเว็บ** (ฟรี) ว่าโควตาใกล้หมด

เดือนนี้ระบบเงียบไปโดยไม่มีใครรู้จนกระทั่งมีคนสังเกตเอง — ตัวนี้แก้ตรงนั้น

**กันไว้ 30 ข้อความ** เพื่อให้ยังมีที่สำหรับเรื่องด่วนจริง ๆ ที่อาจเกิดปลายเดือน

## ผลที่คาดการณ์

| | ปัจจุบัน | หลังแก้ |
|---|---|---|
| admin fan-out | 300 | **~55** (3 คน × ~18-20 วันที่มีของค้าง) |
| แจ้งพนักงาน (ผลการตัดสิน) | 129-165 | คงเดิม |
| สลิปเงินเดือน | 35-48 | **0** |
| **รวม (ใช้ตัวเลข มิ.ย. ซึ่งยุ่งกว่า)** | **579** | **~220 (73%)** |

รองรับพนักงานได้ถึง ~70 คนก่อนจะตันอีก และการเพิ่มแอดมินมีต้นทุนแค่
~20 ข้อความ/เดือนต่อคน แทนที่จะเป็น ~122

## Non-goals (YAGNI)

- ไม่ digest ฝั่งพนักงาน — 3.4 ครั้ง/คน/เดือน กระจายทั้งเดือน แทบไม่มีวันที่
  คนเดียวได้ 2 เรื่อง ประหยัดได้ ~10% แต่ทำให้ผลการอนุมัติมาช้าขึ้นเป็นวัน
- ไม่ทำ digest 2 รอบ/วัน — คำนวณแล้ว 3 × 2 × 22 = 132 ทำให้รวมเป็น ~297 ซึ่งตึงเกินไป
- ไม่ย้ายไปแผนเสียเงิน (ยังเป็นตัวเลือกที่เปิดอยู่ แต่ไม่ใช่งานนี้)
- ไม่แตะ `notifyAdminsInApp` — กระดิ่งในเว็บฟรีและยังเรียลไทม์เหมือนเดิม
- ไม่แก้ schema

## Architecture

### ส่วน 1 — Digest

**`src/lib/inngest/functions/admin-daily-digest.ts`** *(ใหม่)*

```
cron: 'TZ=Asia/Bangkok 30 9 * * *'
```

1. หาแอดมินที่ผูก LINE + ถือ `liff.admin` — **ใช้ predicate เดียวกับ
   `notifyAdminsOnLine`** (`src/lib/notifications/admin-line.ts:19-35`)
   โดยแยกออกมาเป็นฟังก์ชันร่วม ห้าม copy เงื่อนไข
2. ต่อแอดมินหนึ่งคน: `loadSidebarBadgeCounts(assignments)` → `{leave, advance, attendance}`
3. `leave + advance + attendance === 0` → **ข้าม ไม่ส่ง**
4. ส่ง Flex หนึ่งใบ สรุปสามตัวเลข + ลิงก์เข้า `/liff/admin`

เพิ่ม kind ใหม่ `admin.daily-digest` ใน `NotificationPayload` พร้อม template

### ส่วน 2 — เลิก fan-out เรียลไทม์

ลบการเรียก `notifyAdminsOnLine` ทั้ง 4 จุด:
- `src/lib/leave/actions.ts:310`
- `src/lib/advance/actions.ts:163`
- `src/lib/advance/admin.ts:584`
- `src/lib/attendance/check-in.ts:404`

**คง `notifyAdminsInApp` ทุกจุดไว้เหมือนเดิม** — กระดิ่งในเว็บฟรีและเรียลไทม์

ลบการเรียก `notifyPublishedSlips` ใน `src/lib/payroll/run.ts`

`notifyAdminsOnLine` เองยังคงอยู่ (digest ใช้เส้นทางส่งเดียวกัน) แต่จะไม่มี
ใครเรียกแบบ per-event อีก

### ส่วน 3 — ตัวกันโควตา

**`src/lib/line/quota.ts`** *(ใหม่)*

```ts
/** ข้อความที่กันไว้ให้เรื่องด่วนปลายเดือน */
export const QUOTA_RESERVE = 30;

/** null = ตรวจไม่ได้ (ให้ push ต่อ — ไม่บล็อกเพราะ API ล่ม) */
export async function remainingQuota(): Promise<number | null>;
export async function hasQuotaHeadroom(): Promise<boolean>;
```

- เรียก `/v2/bot/message/quota` + `/quota/consumption` (**สอง endpoint นี้
  ไม่กินโควตาเอง**)
- cache ในหน่วยความจำ ~5 นาที เพื่อไม่ให้เรียกทุกครั้งที่ push
- **ถ้า API ล่มหรือตอบไม่ได้ → คืน `null` แล้วปล่อยให้ push ต่อ** อย่าให้
  ตัวกันกลายเป็นตัวบล็อกเสียเอง

**`src/lib/inngest/functions/line-push.ts`** — ก่อน step `push-to-line`:
เช็ค `hasQuotaHeadroom()` ถ้าไม่มีที่ว่าง → mark notification เป็น skipped
พร้อมเหตุผล, แจ้งแอดมินในแอป, **และไม่ throw** (ไม่ใช่ความผิดพลาด จึงไม่ควร retry)

## Testing

**Unit**
- ตรรกะ digest (pure): counts ทั้งสามเป็น 0 → ไม่ส่ง; มีอย่างน้อยหนึ่ง → ส่ง;
  ข้อความมีตัวเลขครบสามตัว
- `remainingQuota` — คำนวณจาก value − totalUsage; API error → `null`;
  `hasQuotaHeadroom` คืน true เมื่อ `null` (fail-open)
- recipient predicate ใช้ร่วมกันจริง (digest กับ notifyAdminsOnLine ได้รายชื่อเดียวกัน)

**Regression:** ชุดเทสต์ทั้งหมดต้องผ่าน (ฐาน 1316 unit + 118 integration)

**Manual smoke:** trigger digest ด้วยมือแล้วดูว่า (ก) วันที่ไม่มีของค้างไม่ส่ง
(ข) วันที่มีของค้างส่งใบเดียวต่อแอดมิน (ค) ตัวเลขตรงกับ badge ในเว็บ

## Reversibility

- ไม่มี schema change / migration
- การลบ fan-out เป็นการ *ลบการเรียก* — กู้คืนได้ด้วยการใส่กลับ 5 บรรทัด
- digest เป็น cron ใหม่ ปิดได้โดยไม่กระทบอย่างอื่น
- ตัวกันโควตา fail-open โดยออกแบบ — ถ้าพัง ระบบกลับไปทำงานเหมือนเดิม
- ไม่มีคำสั่งเขียน/ลบข้อมูลใหม่ (นอกจาก Notification rows ที่มีอยู่แล้วตามปกติ)
