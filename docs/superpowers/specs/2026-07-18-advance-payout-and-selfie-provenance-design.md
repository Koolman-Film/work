# หน้าจ่ายเงินเบิก + ที่มาของรูปเซลฟี่ — Design

**Date:** 2026-07-18
**Status:** Approved (design), pending implementation
**Author:** brainstormed with Claude

## Summary

แก้ 3 รายการที่ลูกค้าแจ้ง และยืนยันแล้วว่าเป็นปัญหาจริงทั้งหมด:

1. **คนจ่ายเงินมองไม่เห็นเลขบัญชี** — ต้องออกจากหน้าจ่ายไปหาที่อื่น
2. **สลิปโอนเงินบังคับแนบ** — ลูกค้าขอให้ไม่บังคับ
3. **เช็คอินใช้รูปจากแกลเลอรีได้** ผ่านเส้นทางสำรองเมื่อกล้องเปิดไม่ได้

ไม่มี schema migration ไม่แตะสูตรเงินเดือน

## Context

### 1+2 — หน้าจ่ายเงินเบิก

ลูกค้าเขียนไว้ตรง ๆ:
> *"2. การจ่ายเงินตามข้อ 1 // แสดงสถานะ อนุมัติ จ่ายเงินแล้ว — แสดงข้อมูล
> ธนาคาร เลขบัญชี ชื่อบัญชี — แนบสลิปโอนเงิน (ไม่บังคับ)"*

ตรวจแล้วพบว่า:
- `ADVANCE_SELECT` (`advance-row-vm.ts:9`) และ `ADVANCE_DETAIL_SELECT`
  (`liff/admin/advance/[id]/_load.ts:7`) **ไม่ได้ select ฟิลด์ธนาคารเลย**
  ทั้งที่ `Employee.bankId/bankAccountNumber/bankAccountName`
  (`schema.prisma:405-408`) มีครบ และมีโมเดล `Bank` พร้อม `nameTh/nameEn/shortName`
- `markAdvancePaid` (`advance/admin.ts:330`) รับ `receiptKey: string` แบบบังคับ
  และ `paidAt` ถูกเซ็ตอยู่ใน `update` เดียวกับ `receiptUrl` เท่านั้น
  (`admin.ts:390-393`) → **ไม่มี code path ไปถึงสถานะจ่ายแล้วโดยไม่แนบไฟล์**
- **เจอเพิ่มระหว่างสำรวจ:** ฝั่งเว็บแอดมินไม่ได้ select `paidAt` ด้วยซ้ำ จึง
  แยกไม่ออกว่า "อนุมัติแล้ว" กับ "จ่ายเงินแล้ว" ต่างกันอย่างไร (ฝั่ง LIFF select มา)

### 3 — ที่มาของรูปเซลฟี่

ลูกค้าแจ้ง:
> *"ตำแหน่งเช็คอิน อยู่นอกพื้นที่ แต่รูปที่ใช้เป็นรูปในพื้นที่ ... เราสามารถ
> แก้ไขให้ใช้รูปที่ถ่ายได้เท่านั้น (ไม่ให้เลือกรูปจากแกลลอรี่)"*

`selfie-step.tsx` ใช้ `getUserMedia` เป็นทางหลัก (ไม่มีทางเข้าถึงแกลเลอรี) แต่
เมื่อกล้องล้มเหลวจะ fallback ไป `<input type="file" accept="image/*" capture="user">`
(`selfie-step.tsx:282-290`) ซึ่ง `capture` เป็นเพียง *คำแนะนำ* ไม่ใช่การบังคับ —
Android หลายรุ่นยังให้เลือกจากแกลเลอรีได้ และฝั่ง server ไม่ได้ตรวจอะไรเพิ่ม

**ช่องโหว่เปิดโดยการทำให้ระบบพัง ไม่ใช่การเจาะระบบ** — แค่กดปฏิเสธสิทธิ์กล้อง
ก็ตกลงเส้นทางสำรองแล้ว

## Decision

### 1+2 — เติมข้อมูลธนาคาร และปลดล็อกสลิป

- ดึงข้อมูลธนาคารมาแสดงบนหน้าที่แอดมิน**กดจ่ายเงินจริง** ทั้งฝั่งเว็บและ LIFF
- ทำให้ `receiptKey` เป็น optional — จ่ายโดยไม่แนบสลิปได้ และแนบทีหลังได้
- ฝั่งเว็บแอดมิน select `paidAt` เพิ่ม เพื่อแยกสถานะ "รอจ่ายเงิน" กับ "จ่ายแล้ว"

**จงใจไม่รวม: แสดงชื่อคนอนุมัติ** — `approvedById` (`schema.prisma:614`) เป็น
คอลัมน์เปล่า ไม่มี relation ไป `User` จึงต้อง query เพิ่มอีกชุด และเรื่องนี้
ลูกค้าไม่ได้ขอ (เป็นของที่คิดเพิ่มเอง) เก็บไว้ทำพร้อมกับการตัดสินใจเรื่อง
บังคับแยกหน้าที่ ซึ่งเป็นงานเดียวกันโดยธรรมชาติ

### 3 — ติดธง ไม่ปิดกั้น

เลือกแนวทาง **"เก็บเส้นทางสำรองไว้ แต่ติดธงว่าต้องตรวจสอบ"**

เหตุผล: ปัจจุบัน**ไม่มีการบันทึกเลย**ว่าเช็คอินไหนมาจากเส้นทางสำรอง จึงไม่รู้ว่า
เกิดบ่อยแค่ไหน การตัดทิ้งทันทีอาจทำให้คนจำนวนมากเช็คอินไม่ได้โดยไม่รู้ตัว
ติดธงก่อนจะได้เห็นตัวเลขจริง แล้วค่อยตัดสินใจตัดทิ้งทีหลังบนข้อมูล

- client แจ้ง server ว่ารูปมาจากทางไหน (`live` / `fallback`)
- ถ้าเป็น `fallback` → บังคับ `checkInStatus = 'Disputed'` เข้าคิว "ต้องตรวจสอบ"
- **ธงนี้เพิ่มการตรวจสอบได้อย่างเดียว ห้ามลดทอน** — ถ้า GPS ตัดสินว่า
  Disputed อยู่แล้ว ให้คงเหตุผลเดิมของ GPS ไว้ (เจาะจงและแก้ได้จริงมากกว่า)

## ข้อจำกัดที่ยอมรับ (สำคัญ — ต้องบันทึกไว้)

ธง `selfieCapture` มาจาก **client** ผู้ใช้ที่ตั้งใจโกงและแก้ request ได้ ย่อม
อ้างว่าเป็น `live` ได้ → **นี่คือเครื่องมือ "ตรวจจับ" ไม่ใช่ "บังคับ"**

ยอมรับได้เพราะสอดคล้องกับแนวทางที่เลือก (ติดธง ไม่ปิดกั้น) และยกระดับความยาก
จาก "กดปฏิเสธสิทธิ์กล้อง" เป็น "ต้องดัดแปลง request" ซึ่งต่างกันมากในทางปฏิบัติ
ถ้าต้องการการบังคับจริงต้องตัดเส้นทางสำรองทิ้ง ซึ่งเป็นการตัดสินใจแยกต่างหาก

## Non-goals (YAGNI)

- ไม่บังคับให้คนอนุมัติกับคนจ่ายเป็นคนละคน (เป็นนโยบาย รอเจ้าของตัดสิน)
- ไม่ตัดเส้นทางสำรองของกล้องทิ้ง
- ไม่ตรวจ EXIF ฝั่ง server (ปลอมได้ และรูปจากเบราว์เซอร์มักไม่มี EXIF อยู่แล้ว)
- ไม่แก้ schema / migration
- ไม่แตะสูตรเงินเดือนหรือการหักเงิน

## Architecture

### ส่วน 1+2 — หน้าจ่ายเงินเบิก

**`src/app/(admin)/admin/advance/advance-row-vm.ts`**
เพิ่มใน `ADVANCE_SELECT`:
```ts
  paidAt: true,
  employee: {
    select: {
      firstName: true, lastName: true, nickname: true,
      bankAccountNumber: true,
      bankAccountName: true,
      bank: { select: { nameTh: true, shortName: true } },
      branch: { select: { name: true } },
      department: { select: { name: true } },
    },
  },
```
แล้วส่งต่อลง VM เป็นฟิลด์ที่ client แสดงได้ตรง ๆ

**`src/app/(liff)/liff/admin/advance/[id]/_load.ts`** — เพิ่มชุดเดียวกัน

**การแสดงผล** — บล็อก "โอนเข้าบัญชี" บนหน้าจ่ายเงิน:
```
ธนาคาร      กสิกรไทย
เลขบัญชี     123-4-56789-0
ชื่อบัญชี     วีระ กล้าหาญ
```
ถ้าไม่มีข้อมูลธนาคาร แสดงข้อความชัดเจนว่า *"ยังไม่ได้กรอกข้อมูลบัญชีธนาคาร"*
พร้อมลิงก์ไปหน้าแก้ไขพนักงาน — **ห้ามแสดงช่องว่างเปล่า** เพราะคนจ่ายจะไม่รู้ว่า
ระบบพังหรือข้อมูลไม่มี

**`src/lib/advance/admin.ts` — `markAdvancePaid`**
```ts
export async function markAdvancePaid(input: {
  cashAdvanceId: string;
  /** optional — จ่ายก่อนแล้วแนบสลิปทีหลังได้ */
  receiptKey?: string | null;
}): Promise<MarkPaidResult>
```
- ตรวจ path ของ `receiptKey` เฉพาะเมื่อมีค่า (คงการตรวจ `authUserId/advance-receipts/` เดิม)
- `paidAt` เซ็ตเมื่อยังเป็น null เสมอ ไม่ขึ้นกับว่ามีสลิปหรือไม่
- `receiptUrl` เขียนเฉพาะเมื่อมี `receiptKey`
- คง gate เดิมทุกตัว: `requirePermission('advance.approve')`, branch scope,
  ต้อง `status = 'Approved'`, audit log

**UI** — ปุ่ม "บันทึกว่าจ่ายแล้ว" ที่ใช้ได้โดยไม่ต้องเลือกไฟล์ และยังคงปุ่ม
แนบสลิปไว้ (ใช้ได้ทั้งก่อนและหลังกดจ่าย)

**ต้องแก้คอมเมนต์ใน schema ด้วย** — `schema.prisma:618` เขียนไว้ว่า
*"receiptUrl + paidAt together mean 'money sent'"* ซึ่งจะไม่จริงอีกต่อไป
หลังงานนี้ `paidAt` เพียงตัวเดียวหมายถึงจ่ายแล้ว ส่วน `receiptUrl` เป็น
หลักฐานเสริมที่มีหรือไม่มีก็ได้ (แก้เฉพาะคอมเมนต์ ไม่แตะโครงสร้างตาราง
จึงไม่เกิด migration)

### ส่วน 3 — ที่มาของรูปเซลฟี่

**`src/lib/attendance/check-in.ts`**
```ts
export type SelfieCapture = 'live' | 'fallback';

export type SubmitCheckInInput = CheckInPoint & {
  selfieKey?: string | null;
  /**
   * วิธีที่ได้รูปมา — `fallback` คือกล้องสดใช้ไม่ได้ จึงตกไปใช้ช่องเลือกไฟล์
   * ซึ่งบางเครื่องเลือกรูปจากแกลเลอรีได้ ค่านี้มาจาก client จึงเชื่อถือได้
   * เท่าที่ client ซื่อสัตย์ — ใช้เพื่อ "ตรวจจับ" ไม่ใช่ "บังคับ"
   */
  selfieCapture?: SelfieCapture;
};
```

ตรรกะหลังคำนวณ `verdict` (ประมาณบรรทัด 216):
```ts
// ธงนี้เพิ่มการตรวจสอบได้อย่างเดียว ห้ามลดทอน: ถ้า GPS ตัดสิน Disputed
// อยู่แล้ว ให้คงเหตุผลของ GPS ไว้ เพราะเจาะจงและแก้ได้จริงมากกว่า
const viaFallback = input.selfieCapture === 'fallback' && selfieKey != null;
const status = verdict.status === 'Disputed' || viaFallback ? 'Disputed' : 'Confirmed';
const disputeReason =
  verdict.status === 'Disputed'
    ? disputeReasonText(verdict.reason)
    : viaFallback
      ? 'รูปเซลฟี่ไม่ได้มาจากกล้องสด — อาจเลือกจากแกลเลอรี'
      : null;
```

**`src/app/(liff)/liff/check-in/selfie-step.tsx`** — `onConfirm` ส่งวิธีจับภาพ
ไปด้วย: `onConfirm(file, cameraFailed ? 'fallback' : 'live')`

**`check-in-client.tsx:143`** — ส่งต่อเข้า `submitCheckIn({ ..., selfieCapture })`

**ข้อความผลลัพธ์ฝั่ง LIFF** — เพิ่ม key `checkin.disputeReason.selfieFallback`
ใน `messages/th.json` + `en.json` (ภาษาอื่น fallback ตามกลไกเดิม)

**หน้า "ต้องตรวจสอบ" ของแอดมิน** — ไม่ต้องแก้ อ่าน `disputeReason` ที่เก็บไว้อยู่แล้ว

## Testing

**Unit**
- `markAdvancePaid` — จ่ายโดยไม่มี `receiptKey` แล้ว `paidAt` ถูกเซ็ตและ
  `receiptUrl` ยังเป็น null; แนบสลิปทีหลังไม่เปลี่ยน `paidAt` เดิม;
  `receiptKey` ที่ path ผิดยังถูกปฏิเสธ; gate เดิมทั้งหมดยังทำงาน
- ตรรกะธงเซลฟี่ (แยกเป็น pure function ได้เพื่อทดสอบง่าย):
  - `live` + GPS ปกติ → `Confirmed`
  - `fallback` + GPS ปกติ → `Disputed` พร้อมเหตุผลเรื่องเซลฟี่
  - `fallback` + GPS ผิด → `Disputed` และ**คงเหตุผลของ GPS ไว้**
  - `fallback` แต่ไม่มี selfieKey (สาขาไม่บังคับเซลฟี่) → ไม่ติดธง
- VM ของหน้าเบิก — มีข้อมูลธนาคารครบ และเคสไม่มีข้อมูลได้สถานะ "ยังไม่กรอก"

**Regression:** ชุดเทสต์ทั้งหมดต้องผ่าน (ปัจจุบัน 1282 unit + 118 integration)

**Manual smoke**
- หน้าจ่ายเงินเบิกแสดงธนาคาร/เลขบัญชี/ชื่อบัญชี
- กด "จ่ายแล้ว" โดยไม่แนบสลิป → สถานะเปลี่ยนเป็นจ่ายแล้ว
- แนบสลิปทีหลัง → `paidAt` ไม่เปลี่ยน
- พนักงานที่ไม่มีข้อมูลธนาคาร → เห็นข้อความเตือน ไม่ใช่ช่องว่าง

## Reversibility

- ไม่มี schema change / migration
- `markAdvancePaid` เปลี่ยนจากบังคับเป็น optional — **ผ่อนคลายกฎ ไม่ได้เข้มขึ้น**
  ข้อมูลเดิมที่มีสลิปครบยังถูกต้องทุกแถว
- ธงเซลฟี่มีผลเฉพาะเช็คอิน**ใหม่**เท่านั้น ไม่แตะข้อมูลย้อนหลัง
- ส่วนที่เหลือเป็นการ select เพิ่ม + แสดงผล
- ย้อนกลับได้ด้วยการ revert commit เดียว
