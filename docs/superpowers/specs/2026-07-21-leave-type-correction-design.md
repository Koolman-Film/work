# แก้ประเภทการลาที่ยื่นผิด — Design

**Date:** 2026-07-21
**Status:** Approved (design), pending implementation
**Author:** brainstormed with Claude

## Summary

แอดมินยังไม่มีวิธี**แก้ประเภท**ของใบลาที่อนุมัติไปแล้วเลย — ทั้งโค้ดเบสไม่มีจุดไหน
เขียนทับ `LeaveRequest.leaveTypeId` หลังสร้าง วิธีเดียวที่ทำได้ตอนนี้คือ **void แล้ว
ยื่นใหม่** ซึ่งทำลายประวัติการอนุมัติและสร้าง `Attendance(OnLeave)` ใหม่ทั้งชุด เพื่อแก้
ค่าคอลัมน์เดียว

สเปกนี้เพิ่มการแก้ประเภทแบบ **inline ในโมดัลรีวิวที่แอดมินใช้อยู่แล้ว** พร้อม
**พรีวิวผลกระทบเรื่องเงินก่อนกดยืนยัน** โดยใช้ตรรกะ over-quota ที่มีอยู่แล้ว
(`replayOverQuota`) ไม่มี schema migration

## Context

### ยังไม่มีทางแก้ประเภทเลย

`grep "leaveRequest.update"` เจอเฉพาะ approve/void/recompute — ไม่มีที่ไหนแตะ
`leaveTypeId` การแก้ประเภทจึงเป็นความสามารถใหม่ล้วน ๆ

### เงินเป็นสองกองที่คนละพฤติกรรม

`chargedMinutes` / `overQuotaMinutes` / `deductAmount` ถูกแช่แข็งตอนอนุมัติ แต่
`src/lib/leave/recompute.ts` คำนวณสดใหม่สำหรับใบที่**ยังไม่ถูกจ่าย** และใช้ค่าที่แช่ไว้
เฉพาะใบที่ payroll เผยแพร่แล้ว (`deductedInPayrollId != null`) — "จ่ายแล้ว = ล็อก"

| กอง | เงื่อนไข | พฤติกรรมเมื่อแก้ประเภท |
|---|---|---|
| **ยังไม่จ่าย** | `deductedInPayrollId = null` | คำนวณ over-quota ใหม่ตามประเภทใหม่ได้ |
| **จ่ายแล้ว** | `deductedInPayrollId != null` | **ล็อก — ห้ามแก้** (ดู Decision 1) |

### การหักเงินขึ้นกับ "ลำดับการอนุมัติ" — นี่คือหัวใจของสเปกนี้

`replayOverQuota` (`src/lib/leave/over-quota.ts`) เล่นซ้ำใบลาของ (พนักงาน, ประเภท,
ปี) **เรียงตาม `reviewedAt ?? createdAt`** สะสม `used` ไปเรื่อย ๆ การหักตกกับใบที่
บังเอิญข้ามเส้นสิทธิพอดี — ไม่ใช่ใบที่ "ผิดที่สุด"

**ผลคือการแก้ประเภทหนึ่งใบไม่ใช่การแก้เฉพาะที่:**

- **ถอด**ใบนั้นออกจากกลุ่มประเภทเดิม → ใบ**ที่อยู่หลังมัน**ในกลุ่มเดิมมี `used` ลดลง
  บางใบอาจเปลี่ยนจาก "ถูกหัก" เป็น "ไม่ถูกหัก"
- **แทรก**ใบนั้นเข้ากลุ่มประเภทใหม่ตามตำแหน่ง `reviewedAt` → อาจดันใบที่อยู่หลัง
  ในกลุ่มใหม่ให้ข้ามสิทธิ

ตัวอย่างจริง: แก้ใบ "ฉันไม่สบาย" ของ AUNG (฿633) จากลากิจ→ลาป่วย ไม่ได้แค่ทำใบนั้น
เป็น ฿0 แต่ยัง**คืนสิทธิลากิจ 1 วัน** ซึ่งอาจปลดการหักของใบลากิจใบอื่นของเขาที่อยู่
ถัดไปในปีเดียวกัน

**นี่คือพฤติกรรมที่ถูกต้องและเป็นผลดีกับพนักงาน** แต่แปลว่า UI ที่โชว์แค่
"฿633 → ฿0" กำลังโกหกด้วยการละเว้น — พรีวิวต้องแสดง ripple ข้ามทั้งสองประเภท
ของพนักงาน-ปีนั้น ไม่ใช่แค่แถวที่กำลังแก้

### สิ่งที่ reuse ได้

- `replayOverQuota` — สูตร over-quota แบบ pure ที่ unit-test แล้ว
- `ReviewModal` (`src/app/(admin)/admin/leave/leave-review-modal.tsx`) — ที่ที่
  แอดมินสังเกตเห็นว่าประเภทผิดอยู่แล้ว
- `overQuotaPreview` (`src/lib/leave/approval-preview.ts`) — pattern พรีวิวเงิน
- `recompute.ts` — pattern "เขียนเฉพาะใบที่ยังไม่จ่าย ข้ามใบที่ swept"
- segmented-button pattern จากสเปก leave-type-selection-ux

## Decision

### 1. ห้ามแก้ใบที่จ่ายแล้วโดยเด็ดขาด

`deductedInPayrollId != null` → ปุ่มแก้ประเภทถูก disable พร้อมข้อความ
"จ่ายแล้ว — แก้ไขไม่ได้" และ **server action ตรวจซ้ำใน transaction** เพราะ state
ใน UI อาจ stale (payroll เผยแพร่ระหว่างเปิดโมดัลค้างไว้)

รักษา invariant "จ่ายแล้ว = ล็อก" ที่ทั้ง payroll design พึ่งอยู่ ไม่มี refund
ไม่เปิด reopened month การได้เงินคืนของใบที่จ่ายแล้ว (15 ใบ, ฿4,873) เป็นงาน
คนละชิ้น — payroll adjustment — ไม่อยู่ในสเปกนี้

### 2. เงื่อนไขที่จะเสนอให้แก้ประเภท

ทั้งหมดต้องจริง: `status = 'Approved'` · `deletedAt = null` ·
`deductedInPayrollId = null` · ประเภทใหม่ ≠ ประเภทเดิม

ใบ Pending ไม่ต้องใช้ฟีเจอร์นี้ — แอดมินเปลี่ยนตอนอนุมัติได้อยู่แล้ว (และจะง่ายขึ้น
เมื่อสเปก leave-type-selection-ux ขึ้น)

### 3. พรีวิว ripple ก่อนยืนยัน — ฟังก์ชัน pure ใหม่

`previewTypeCorrection(requestId, newTypeId)` เรียก `replayOverQuota` **สองครั้ง**:

1. กลุ่มเดิม (พนักงาน, ประเภทเดิม, ปี) โดย**ถอด**ใบที่แก้ออก
2. กลุ่มใหม่ (พนักงาน, ประเภทใหม่, ปี) โดย**แทรก**ใบที่แก้ตามลำดับ `reviewedAt`

คืนรายการ before/after ต่อใบ (ทุกใบที่ค่าเปลี่ยน ทั้งสองกลุ่ม) + ยอดสุทธิ
เป็น pure ไม่มี I/O — จุดที่ unit test มีค่าที่สุด

**ปี (`periodYear`)** อิงจาก `startDate` ของใบ ตรงกับที่ `recompute.ts` จัดกลุ่ม

### 4. Transaction — atomic ทั้งสองกลุ่ม

1. โหลดใบ + ตรวจ Decision 2 เงื่อนไขซ้ำ (กัน race)
2. เขียน `leaveTypeId` = ประเภทใหม่
3. เขียน `overQuotaMinutes` / `deductAmount` ที่คำนวณใหม่ให้**ทุกใบที่ยังไม่จ่าย**
   ในทั้งสองกลุ่ม (ใบที่ swept เก็บค่าแช่แข็งไว้ แต่ยังนับกิน quota — เหมือน
   `recompute.ts` เป๊ะ)
4. `chargedMinutes` **ไม่เปลี่ยน** — วันและ unit เท่าเดิม เปลี่ยนแค่การแบ่ง
   over-quota (เขียนไว้ชัด ๆ กันคนมา "แก้" ทีหลัง)
5. audit log หนึ่งรายการ: before/after ทั้งชุด + โน้ตที่บังคับกรอก

### 5. UI — ในโมดัลรีวิวเดิม

ส่วน "เปลี่ยนประเภท" ใน `ReviewModal`: ตัวเลือกประเภท (segmented buttons) →
ตารางพรีวิว ripple → ช่องโน้ต (บังคับ) → ยืนยัน ไม่มีหน้าใหม่ให้ไป

ใบที่จ่ายแล้ว: ส่วนนี้ render แบบ disabled พร้อมเหตุผล

### 6. Permission ใหม่ `leave.correct-type`

ให้ Admin โดยดีฟอลต์ คู่กับ `leave.void` แยก key เพราะมัน**ขยับเงิน** ควร grant
แยกจาก `leave.approve` ได้ ตามสไตล์ fine-grained ที่มีอยู่ (`leave.void`,
`leave.entitlement.manage`)

## Non-goals (YAGNI)

- **ไม่แตะใบที่จ่ายแล้ว ไม่คืนเงินย้อนหลัง** — Decision 1
- **ไม่แจ้งพนักงานผ่าน LINE ใน v1** — แยกได้ และสลิปจะสะท้อนการเปลี่ยนอยู่แล้ว
- **ไม่ทำหน้า batch correction** — backlog จริงมี ~4 ใบที่ผิดจริง batch UI แก้ปัญหา
  scale ที่ไม่มีอยู่ (ดู "ที่มา" ด้านล่าง)
- **ไม่แก้ quota/policy ของลากิจ** — ~฿13k ของยอดที่ถูกหักเป็นลากิจที่ยื่น**ถูก**
  (พาสปอร์ต สมาร์ทการ์ด ใบขับขี่) นั่นเป็นคำถามเรื่อง quota คนละเรื่องกับสเปกนี้
- **ไม่แก้ entitlement ที่เป็น 0** — พี่แดง (พิรุฬห์ลักษณ์) มีสิทธิ 0 ทุกประเภทปี
  2026 ต่างจากคนอื่นที่ได้ 30/3 อาจตั้งใจ (พนักงานใหม่/สัญญาต่าง) — ไม่แตะโดยไม่ถาม
- **ไม่เปลี่ยนสูตรเงิน สิทธิ หรือ over-quota ใด ๆ** — reuse `replayOverQuota` เดิม
- **ไม่ void/re-file** — Approach B ถูกปฏิเสธ: churn `Attendance(OnLeave)` ทั้งชุด
  เพื่อแก้คอลัมน์เดียว

## ที่มา (production 2026-07-21)

จาก 23 ใบยังไม่จ่ายที่ถูกหัก (฿18,265) อ่านเหตุผลทั้งหมด:

- **ประเภทผิดจริง ~฿2,217 (4 ใบ):** "ฉันไม่สบาย", "เจ็บตา", "หมอนัด...", "ลาป่วย" —
  ทุกใบมีสิทธิลาป่วย 30 วันเหลือเกือบเต็ม แก้แล้วเป็น ฿0 จริง
- **ก้ำกึ่ง ~฿2,042:** พาพ่อ/แม่ไปหาหมอ — ลากิจอาจถูกอยู่แล้ว
- **ลากิจที่ยื่นถูก ~฿13,107 (72%):** พาสปอร์ต/สมาร์ทการ์ด/เอกสารตรวจคนเข้าเมือง
  ~฿10,633, ใบขับขี่ ×4, สอบ, ขึ้นศาล, ประชุมผู้ปกครอง — ลากิจถูกต้องทุกใบ

ลากิจครองยอดหัก **ไม่ใช่**เพราะคนพลาดมาลงตรงนี้ แต่เพราะเป็นประเภทเดียวที่ quota
เล็กพอจะเกิน (3 วัน เทียบลาป่วย 30) การแก้ประเภทจึงคืนเงินได้อย่างมาก ~12% ของยอด
ฟีเจอร์นี้แก้ "ประเภทผิด" ไม่ใช่ "quota เล็ก" — คนละปัญหา

## Reversibility

- ไม่มี schema migration
- ทุกการแก้มี audit log before/after ครบ — reverse ได้ด้วยการแก้กลับ
- ใบที่จ่ายแล้วแตะไม่ได้ตั้งแต่แรก → ไม่มีทางกระทบเดือนที่ปิดแล้ว
- `chargedMinutes` ไม่ขยับ → จำนวนวันลาที่บันทึกไว้เท่าเดิม

## Testing

**Pure/unit — `previewTypeCorrection` (จุดที่มีค่าที่สุด):**
- ถอดใบกลางกลุ่ม → ใบที่อยู่หลังในกลุ่มเดิมเปลี่ยนจากถูกหักเป็นไม่ถูกหัก
- แทรกใบเข้ากลุ่มใหม่ → ดันใบที่อยู่หลังในกลุ่มใหม่ให้ข้ามสิทธิ
- ใบ swept ในกลุ่มใด ๆ: เก็บค่าแช่แข็ง แต่ยังนับกิน quota
- ประเภทใหม่ `grantedMinutes = null` (ไม่จำกัด) → ไม่มีใบไหนถูกหัก
- ประเภทใหม่ entitlement = 0 (เคสพี่แดง) → **ยังถูกหัก** พรีวิวต้องไม่โชว์เป็น ฿0
- ประเภทใหม่ = ประเภทเดิม → ปฏิเสธ (no-op)

**Integration:**
- server action ปฏิเสธใบที่ `deductedInPayrollId != null` แม้ UI ส่งมา (กัน race)
- transaction เขียนทั้งสองกลุ่มแบบ atomic — ล้มกลางคันแล้วไม่มีอะไรค้าง
- audit log บันทึก before/after ครบทุกใบที่เปลี่ยน + โน้ต
- ต้องมี permission `leave.correct-type` ถึงเรียกได้ (branch-scope เหมือน void)

**Manual (เบราว์เซอร์):**
- เปิดใบลากิจที่ถูกหัก → เปลี่ยนเป็นลาป่วย → พรีวิวโชว์ ripple ทั้งสองประเภท →
  ยืนยัน → ยอดในรายงานตรงกับพรีวิว
- ใบที่จ่ายแล้ว: ส่วนแก้ประเภท disabled พร้อมเหตุผล
- ทดสอบภาษาที่ไม่ใช่ไทยหนึ่งภาษา — ป้ายต้องแปล

**Regression:** ชุดเทสต์ทั้งหมดต้องผ่าน (ฐาน 1,414 unit + integration)

## ลำดับกับสเปกอื่น

อิสระจาก `leave-type-selection-ux` และ `cutoff-window-dispute-quota` — คนละไฟล์
คนละกลไก ขึ้นก่อนหรือหลังก็ได้ แต่ทั้งคู่แก้ "ประเภทผิด" จากคนละด้าน (ป้องกันตอน
ยื่น vs แก้หลังยื่น) — ปล่อยพร้อมกันได้

## Deploy

อยู่ใต้ freeze เดียวกับทุกอย่าง — **ห้าม deploy ก่อนรอบเงินเดือน 2026-07 ปิด
(cutoffDay = 26)** แก้ประเภทได้เฉพาะใบที่ยังไม่จ่าย ยิ่งต้องรอให้รอบปัจจุบันจบ
บนโค้ดที่ใช้อยู่ก่อน
