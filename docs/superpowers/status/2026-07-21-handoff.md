## 4. เรื่องที่ต้องให้ลูกค้าตัดสิน — ยังไม่ได้ถาม

### 4.1 ประเภทการลาผิด และเงินที่หักไปแล้ว ~฿22,600

ระบบ**เลือก "ลากิจ" ให้พนักงานทุกคนทุกครั้ง** (ผลข้างเคียงของ `orderBy: name` +
`leaveTypes[0]`; ลากิจเรียงมาก่อนตามตัวอักษรไทย และมีสิทธิน้อยที่สุด 3 วัน/ปี)

```
ปี 2026:  ลากิจ  สิทธิ 3 วัน/ปี  ใช้ไป 55.3 วัน (27 คน)  ← เกินสิทธิ ถูกหักเงิน
          ลาป่วย สิทธิ 30 วัน/ปี ใช้ไป 13.3 วัน (10 คน)  ← เหลือเกือบทั้งหมด

19 รายการที่ถูกหักเงิน — 18 เป็นลากิจ รวม ~฿22,600
```

**รายการที่เหตุผลบอกเองว่าอยู่ผิดประเภท:**

| พนักงาน | ยื่นเป็น | เหตุผลที่เขียน | ถูกหัก |

| พรชัย | ลากิจ | **"ลาป่วย"** | ฿516.67 |
| AUNG | ลากิจ | **"ฉันไม่สบาย"** | ฿633.33 |
| JOMSANG | ลากิจ | "เจ็บตา" | (ใน ฿3,733.33) |
| ภัทธริดา | ลากิจ | "ท้องเสีย" | (ใน ฿1,983.34) |
| พิรุฬห์ลักษณ์ | ลากิจ | "หมอนัด" | ฿450 |

**และรายการที่ไม่ควรเป็นการลาเลย:**

**⚠️ มีใบลารออนุมัติอยู่:** JOMSANG 21 ก.ค. *"หมอนัดกลับไม่ทัน"* ฿533.33 —
**ตัดสินประเภทก่อนกดอนุมัติ** เพราะอนุมัติแล้วยอดจะถูกตรึง

## 5. เรื่องที่รู้แล้วแต่จงใจไม่แก้ (บันทึกไว้กันลืม)

**ของเดิมที่ไม่เกี่ยวกับงานที่ทำ — ควรมีสาขาของตัวเอง:**
- สลิปคำนวณเรทลาสดคู่กับเงินที่ตรึงแล้ว → เปิดสลิปเก่าหลังขึ้นเงินเดือนจะเห็นเรทใหม่
  คู่กับยอดเก่า
- พนักงานรายชั่วโมง: ราคา "หนึ่งวัน" ของค่าปรับกับของวันลาไม่ตรงกัน
- `perMinuteRate` ไม่มี guard ตัวหาร (`workingDaysPerMonth = 0` → `Infinity`)
- formatter เงิน 6 แบบในระบบเดียว
- `Attendance.deductAmount` เป็นคอลัมน์ที่ไม่มีใครเขียน แต่มีหน้าจออ่าน (ช่องว่างถาวร)
- คอมเมนต์ 4 จุดยังเขียนว่า digest ส่ง 09:30 ทั้งที่ย้ายไป 08:30 แล้ว

**ข้อจำกัดที่ตั้งใจ (อยู่ใน runbook):**
- ขาดงาน 27–31 ธ.ค. ตัดสิทธิลา**ปีถัดไป** (เพราะ cutoff 26 ทำให้อยู่ในเดือน `2026-01`)
  ขณะที่ใบลาวันเดียวกันตัดปีปัจจุบัน — **ต้องบอก HR**
- settlement แก้ไม่ได้เมื่อเดือนนั้นเผยแพร่แล้ว (ตั้งใจ — เงินตรึง สิทธิคิดสด)
- ไม่มีฟีเจอร์ยกเลิกการเผยแพร่ และไม่มีใบแก้ไข

## 6. บทเรียนจากเซสชันนี้ที่ควรใช้ต่อ

**รีวิว fix wave ทุกชุดก่อนไปต่อ** — รอบที่ 3 ผมส่ง fixer 3 ชุดแล้วเช็คแค่ว่าเทสต์เขียว
ผลคือ Critical ใหม่ 2 ตัว รอบที่ 4 รีวิวทุกชุด และ 2 wave สุดท้ายไม่เจออะไรเลย
**ตัวแปรคือกระบวนการ ไม่ใช่คุณภาพของโค้ดที่เขียน**

**คำอ้างว่า "แก้ไม่ได้" ต้องตรวจหนักกว่าคำอ้างว่า "แก้แล้ว"** — อย่างหลังมี diff ให้ดู
อย่างแรกไม่มีอะไรให้ดูเลย ในเซสชันนี้มี fixer อ้างว่าแก้ไม่ได้เพราะจะเกิด deadlock
ผมเชื่อและรายงานว่าเป็นการตัดสินใจที่ถูก — จริง ๆ แล้วผิด และเป็นครึ่งหนึ่งของ Critical

**บั๊กที่ร้ายแรงที่สุดอยู่ในไฟล์ที่สาขานั้นไม่ได้แก้** — รีวิวที่ถาม "โค้ดที่เปลี่ยนถูกไหม"
ตอบถูกทุกครั้ง คำถามที่จับได้คือ **"ยังมีที่ไหนอีกที่คำนวณสิ่งเดียวกัน"**

**รันโค้ดจริงทับข้อมูล production ก่อน deploy** — ตอบ "จะพังไหม" ได้ตรงกว่าเทสต์
ทั้งชุด เพราะ input ไม่ได้มาจากคนเขียนเทสต์

**ดูหน้าจอจริง** — I-7 และเรื่องประเภทลาผิดทั้งหมดมาจากภาพหน้าจอที่ผู้ใช้ส่งมา
ไม่มีรีวิวรอบไหนใน 5 รอบไปอ่านฟังก์ชันจัดรูปแบบข้อความ
