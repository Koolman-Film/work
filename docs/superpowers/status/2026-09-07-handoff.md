## 2. The research — read this first

**`docs/research/2026-09-07-thai-accounting-export-formats.md`** (818 lines, sourced, with a
confidence rating per claim). Do not redo it. Its §8 lists 13 things that are genuinely
unverified — that is where new research effort belongs, not the parts already covered.

### The four facts that decide the design

1. **ภ.ง.ด.1 needs no rigid layout from us.** RD Prep — the Revenue Department's own free
   desktop program — imports a delimited *or* fixed-width text file and lets the accountant
   **map columns interactively** (`กำหนดตำแหน่งข้อมูล`), with a first-row-is-column-names
   toggle. A clean pipe-delimited UTF-8 file with a Thai header row is a legitimate v1.
   Matching the official FORMAT 2.0 exactly is a *later* optimisation that buys direct upload
   without RD Prep.
2. **Both statutory layouts ARE public**, contrary to the first research pass:
   - ภ.ง.ด.1 "FORMAT กลาง" **V2.0** — 22-field header, 26-field detail, pipe-delimited.
     Spec states encoding verbatim: **UTF-8, not TIS-620.**
   - สปส.1-10 — fixed-width **135 characters**, plus an official Excel template. Found on
     sso.go.th's *Downloads → โปรแกรมต่างๆ*, **not** in the e-Services manual (that manual
     documents the UI only, which is why it reads as if no spec exists).
3. **Express cannot import journal entries at all.** Vendor-forum staff reply, quoted:
   *"โปรแกรม Express ไม่สามารถโอนหรือนำเข้ารายการเดินบัญชี"*. **Do not build an Express
   journal exporter.** Give Express users a generic CSV/XLSX instead.
4. **Every bank ships a converter.** Target the *converter's input* (usually pasted Excel),
   not a binary file layout. Most bank layouts are customer-only — ask the account holder for
   the spec their bank gave them rather than searching.

## 4. Decisions already made — do not re-litigate

- **Branches are separate registered companies.** Confirmed by the owner. So per-branch
  export is correct, and employer tax identity belongs on **`Branch`** (`taxId`, VAT branch
  no., e-Filing UserID). **No `Company` model is needed.** Record the assumption — a future
  shared-entity branch would break it, and สปส.1-10/1 (multi-branch filing) is the form that
  case needs.
- **Withholding tax should live in payroll**, not stay with the outside accountant.
- **v1 of ภ.ง.ด.1 targets RD Prep's interactive mapper**, not FORMAT 2.0.
- **No Express journal exporter.**

## 5. Suggested build order

Ordered by *data we already have*, which is close to the inverse of prominence.

1. **Bank direct-credit files.** Every field exists (`Bank.code`, `bankAccountNumber`,
   `bankAccountName`, `netPay`). Needs a company bank account + a batch record. Cheapest real
   value. **Get the spec from the bank, don't search for it.**
2. **GL journal export.** Needs the chart-of-accounts mapping (§3) and `incomeOt`. Generic —
   one exporter serves Express (as CSV), PEAK, FlowAccount and everything else.
3. **Fix the shipped สปส.1-10 XLSX** to match SSO's official template — it currently
   concatenates `firstName`/`lastName` into one `ชื่อ-สกุล` column where the template wants
   them split, has extra title/totals blocks, and the worksheet must be named for the branch
   number. Small, independent, and the file already carries its own
   `⚠️ VERIFY BEFORE SHIP` comment.
4. **Withholding tax in payroll** → then ภ.ง.ด.1, ภ.ง.ด.1ก, 50 ทวิ all follow. Largest scope.

Follow the existing statutory-export pattern in
`src/app/(admin)/admin/filings/sso/export/route.ts`: a `filing.export` permission,
branch-scoped, and a **pre-flight 422 that refuses to emit a file when data is incomplete**
(it currently refuses on missing national IDs / employer SSO account). A silently-incomplete
file that someone imports into their books is worse than no file.

## 6. Two defects in shipped code — both verified against the repo

1. **`src/lib/export/csv.ts` must not be reused for statutory files.** Line 9 prepends `'` to
   any cell starting with `= + - @` (formula-injection guard), and it always emits a UTF-8
   BOM. Both correct for the Excel-facing reports it serves. Both **corrupting** for a
   statutory file: RD forbids that character, and the BOM would land inside the first header
   field. Statutory targets need a **separate writer** — per-target encoding, per-target
   delimiter, no BOM, no injection guard, and a character allowlist that *rejects the row*
   rather than silently mangling it. Leave `toCsv` pointed at human-facing reports.
2. **SSO ceiling contradiction.** `prisma/schema.prisma:873-875` asserts ฿15,000 / ฿750
   *"per Thai law"*; `prisma/seed.ts:129-130` uses `17500` / `875`. One is stale. **Not
   resolved** — which is legally current could not be settled from here, and a doc-comment
   should not be asserting a legal fact at all. Needs a human with the gazette reference.
