## I-4 — ตรึงช่วงวันไว้กับเงิน และยึดรอยต่อระหว่างเดือน

### ปัญหา

`payrollMonthWindow(month, cutoffDay)` (`src/lib/payroll/period.ts:17`) คำนวณช่วงวัน
จาก `cutoffDay` **ปัจจุบัน** เสมอ ไม่มีที่ไหนบันทึกว่าเดือนที่ปิดไปแล้วใช้ค่าอะไร

```
มิ.ย. เผยแพร่ด้วย cutoff 25  →  26 พ.ค. – 25 มิ.ย.  (เงินตรึงแล้ว)
เปลี่ยน cutoff เป็น 20
ก.ค. คำนวณด้วย cutoff 20     →  21 มิ.ย. – 20 ก.ค.
                                 └─ 21–25 มิ.ย. อยู่ในทั้งสองเดือน → หักซ้ำ
```

**และเปลี่ยนไปอีกทางก็พังเหมือนกัน** — cutoff 25 → 30 ทำให้ ก.ค. เริ่ม 1 ก.ค.
วันที่ 26–30 มิ.ย. **ไม่อยู่ในเดือนไหนเลย** หายไปจากระบบทั้งการหักและการจ่าย

production แก้ config มาแล้ว 14 ครั้ง — ไม่ใช่การกระทำที่หายาก

### สิ่งที่ตรึงอย่างเดียวแก้ไม่ได้

การเก็บ `cutoffDay` ไว้กับแถวทำให้เดือนที่ปิดแล้ว*พูดความจริง* แต่ไม่ได้ทำให้
วันไม่ทับและไม่หาย — เพราะจุดเริ่มของเดือนถัดไปยังคำนวณจากค่าใหม่

**ต้องมีสองส่วน และทำงานคู่กัน**

### ทางแก้

**1. `Payroll.cutoffDay` — ตรึงค่าที่ใช้ตอนคำนวณแถวนั้น**

```prisma
model Payroll {
  // ...เดิม...
  /// The cutoffDay in force when this row was calculated. Frozen with the
  /// money: a published row's window must never move when an admin edits
  /// PayrollConfig later. Draft rows recalculate live and restamp this.
  cutoffDay Int
}
```

**2. จุดเริ่มของเดือน = วันถัดจากที่เดือนก่อนหน้าจบจริง**

```
ช่วงของเดือน M = {
  เริ่ม: มีเดือน M-1 ที่ไม่ใช่ Draft ?  (จบของ M-1 ตาม cutoffDay ที่ตรึงไว้) + 1 วัน
                                       : สูตรเดิม
  จบ:   ตาม cutoffDay ปัจจุบัน
}
```

**"เดือน M-1 ที่ไม่ใช่ Draft" หมายถึงอะไรกันแน่** — เราเพิ่งทำให้ publish เป็นรายคน
(ข้ามคนที่มี settlement ค้าง ไม่หยุดทั้งเดือน) ดังนั้นเดือนหนึ่งอาจเผยแพร่ไปแล้ว
บางคน จึงต้องระบุให้ชัด: **ยึด `cutoffDay` ที่ตรึงไว้บนแถวที่ไม่ใช่ Draft ของ
*พนักงานคนนั้น*** ไม่ใช่ค่าระดับเดือน

เหตุผล: ถ้ายึดระดับเดือน พนักงานที่ยังไม่ถูกเผยแพร่จะได้ช่วงวันที่อ้างอิงจาก
แถวของคนอื่น ซึ่งไม่มีความหมายกับเขา การยึดรายคนทำให้แต่ละคนต่อเนื่องกับ
เดือนที่ตัวเองปิดไปแล้วจริง ๆ — ซึ่งเป็นสิ่งที่ป้องกันการหักซ้ำของ*คนนั้น*

ถ้าพนักงานคนนั้นไม่มีแถว M-1 ที่ไม่ใช่ Draft (พนักงานใหม่ หรือเดือนก่อนยังไม่ปิด)
→ ใช้สูตรเดิม ไม่มีอะไรให้ต่อเนื่อง

ผลลัพธ์กับทั้งสองทิศ:

```
25→20:  ก.ค. = 26 มิ.ย. – 20 ก.ค.   เดือนสั้นลง ไม่มีวันทับ
25→30:  ก.ค. = 26 มิ.ย. – 30 ก.ค.   เดือนยาวขึ้น ไม่มีวันหาย
```

**ร่างยังคิดสด** ตามหลักของระบบนี้ (Draft สด / เผยแพร่แล้วตรึง) — เฉพาะแถวที่
ไม่ใช่ `Draft` เท่านั้นที่ค่าถูกตรึง Draft จะ restamp `cutoffDay` ทุกครั้งที่คำนวณใหม่

**3. หน้าตั้งค่าเตือนก่อนเปลี่ยน**

บอกตรง ๆ ว่าเดือนถัดไปจะกินกี่วัน (ยาวหรือสั้นกว่าปกติเท่าไร) และเงินเดือน
เดือนนั้นจะไม่เท่าเดิม **ไม่ห้ามเปลี่ยน** — ลูกค้าอาจมีเหตุผลจริง และการห้ามถาวร
จะกลายเป็นข้อจำกัดที่อธิบายไม่ได้

### ผู้เรียกที่ต้องแก้

`payrollMonthWindow` มีผู้เรียก 3 จุด:
- `src/lib/payroll/run.ts:82` — ช่วงที่ใช้คำนวณจริง
- `src/lib/payslip/document.ts:309` — นับรายการลงเวลาบนสลิป (**อ่านสดคู่กับเงิน
  ที่ตรึงแล้ว — ต้องใช้ค่าที่ตรึงไว้ ไม่งั้นสลิปเก่าจะเปลี่ยนตัวเลขเอง**)
- `src/lib/payroll/period.ts:32` — wrapper

## I-2 — ปฏิเสธ = การเช็คอินนี้ไม่จริง

### ปัญหา

คอมเมนต์ใน `src/lib/attendance/admin-review.ts:17-22` เขียนไว้ว่า:

> *"`isOverridden=true` is the breadcrumb that payroll/reporting checks before
> counting this row"* · *"An approved check-in counts as a worked day; a
> rejected one does not."*

`grep checkInStatus|isOverridden src/lib/payroll/` → **ไม่เจอเลย** เงินเดือนไม่รู้จัก
ฟิลด์นี้ทั้งคู่ **โค้ดบันทึกเจตนาที่ไม่มีใครทำต่อ**

ผลจริง: แอดมินกดปฏิเสธ = "คุณไม่ได้มา" แต่รายการเช็คอินยังอยู่ รายการสายที่แตก
จากมันยังอยู่และยังถูกหักเงิน และพนักงานได้เงินเต็มวัน

จากนั้นแอดมินจะไปคีย์ "ขาดงาน" แทน แล้วเจอ:

> *"พนักงานคนนี้มีการเช็คอินของวันนี้อยู่แล้ว จึงบันทึกเป็นขาดงานไม่ได้"*

เพราะ guard ที่ `src/lib/attendance/manual.ts:207` ไม่กรอง `checkInStatus`
**ทางตัน — ไม่มีอะไรบนหน้าจอบอกว่าต้องลบเช็คอินก่อน**

### ทางแก้

`rejectDisputed` ลบ (soft-delete) ทั้ง**รายการเช็คอิน และรายการสายที่แตกจากมัน**
ในวันเดียวกัน — คุณสายไม่ได้ในวันที่คุณไม่ได้มา กู้คืนได้ด้วยปุ่มที่ระบบมีอยู่แล้ว

**"รายการสายที่แตกจากมัน" คือแถวไหน** — ระบบไม่มี FK โยงรายการสายกลับไปหา
รายการเช็คอิน มีแต่ `(employeeId, date)` ร่วมกัน ดังนั้นให้ลบแถว `type: 'Late'`
ที่ยังไม่ถูกลบ ของพนักงานคนเดียวกัน วันเดียวกัน

**ข้อจำกัดที่ยอมรับ:** ถ้าแอดมินคีย์รายการสายด้วยมือแยกต่างหากในวันเดียวกัน
มันจะถูกลบไปด้วย ยอมรับได้เพราะ (ก) วันนั้นกำลังจะถูกบันทึกใหม่ทั้งวันอยู่แล้ว
(ข) เป็น soft-delete กู้คืนได้ และ (ค) การปล่อยรายการสายค้างไว้ในวันที่ตัดสินว่า
พนักงานไม่ได้มา คือความไม่สอดคล้องที่แย่กว่า

จากนั้น**ถามแอดมินทันทีว่าวันนั้นเกิดอะไร** พาไปหน้าคีย์มือพร้อมพนักงานและวันที่
กรอกไว้ให้ — ตัวเลือกที่ต้องการ (ขาดงาน / ทำงานปกติแต่เช็คอินไม่ได้) มีอยู่แล้วทั้งหมด
**ไม่ต้องสร้างหน้าจอใหม่**

**ถ้าแอดมินไม่ตอบ วันนั้นจะว่างและพนักงานได้เงินเต็ม** จึงต้องมีที่ค้างให้เห็น:
ใช้ธงบนหน้ากระทบยอดที่มีอยู่แล้ว — *"มีวันที่ปฏิเสธเช็คอินแล้วยังไม่ได้บันทึกว่า
เกิดอะไรขึ้น"*

**และต้องแก้คอมเมนต์ที่โกหก** ให้บอกความจริงว่าเงินเดือนไม่อ่านฟิลด์นี้ และการ
ปฏิเสธมีผลผ่านการลบรายการ ไม่ใช่ผ่านธง

### ขนาดปัญหาบน production

ปฏิเสธไปแล้ว 1 ครั้งทั้งระบบ · ค้างอยู่ 0 · ไม่มีเคสที่มีรายการสายค้างคู่
แต่การตรวจจับ selfie จากแกลเลอรีเพิ่งขึ้น — จำนวนจะโตขึ้นแน่

## I-6 — ลดโอกาสตก มากกว่าไล่ส่งซ้ำ

### ปัญหา

`QUOTA_RESERVE = 5` (`src/lib/line/quota.ts:32`) เป็นค่าคงที่ ขณะที่ digest ตอน
08:30 ยิงข้อความพร้อมกันเท่าจำนวนแอดมินที่ผูก LINE และตัวนับโควตาแคช 5 นาที
โดย**ไม่ลดค่าหลังส่ง** — ข้อความในชุดเดียวกันจึงอ่านค่าเดิมทุกใบ ส่งเกินได้เท่ากับ
จำนวนแอดมิน − 1

เมื่อโควตาหมด `line-push.ts` ทำเครื่องหมาย `skipped='quota'` ปล่อย `sentAt` เป็น
null และ**ไม่ throw** (ถูกแล้ว — ถ้า throw Inngest จะ retry การปฏิเสธที่ตั้งใจ)
แต่ไม่มีอะไรไล่ส่งใหม่ และ**ไม่มีหน้าจอไหนบอกว่าใครไม่ได้รับ**

### ทางแก้

**1. `QUOTA_RESERVE` คำนวณจากจำนวนแอดมินที่ผูก LINE + เผื่อ** แทนค่าคงที่ —
เพราะตัวเลขที่ถูกต้องคือ "หนึ่งชุด digest" ซึ่งโตตามจำนวนแอดมิน

**2. แสดงรายการที่ถูกทิ้งให้แอดมินเห็น** — ใครไม่ได้รับอะไรเมื่อไร

**ไม่ทำระบบส่งซ้ำอัตโนมัติ** — ข้อความ *"อนุมัติลาแล้ว"* ที่ค้างมา 5 วันเป็นขยะ
ไม่ใช่ข้อมูล และการปล่อยให้ค้างสะสมแล้วไหลออกวันที่ 1 ของเดือนคือการสร้าง
ปัญหาใหม่ ให้แอดมินเห็นแล้วตัดสินเองว่าจะบอกด้วยวิธีอื่นไหม

## Non-goals (YAGNI)

- ไม่ห้ามเปลี่ยน `cutoffDay`
- ไม่ทำ effective-date ให้ `cutoffDay` (เก็บค่าใหม่ไว้ให้มีผลเดือนถัดไป) — ซับซ้อน
  กว่าที่ปัญหาต้องการ และเดือนคร่อมยังยาว/สั้นอยู่ดี
- ไม่บันทึกขาดงานอัตโนมัติเมื่อปฏิเสธข้อพิพาท — ระบบไม่รู้ว่าวันนั้นเกิดอะไร
- ไม่ทำระบบส่งซ้ำข้อความ LINE อัตโนมัติ
- ไม่แตะสูตรเงินเดือน ไม่แตะการหักสิทธิที่เพิ่ง merge ไป
- ไม่ย้อนแก้ข้อมูลเก่า

## Reversibility

- migration เพิ่มคอลัมน์เดียวพร้อม default — rollback = `DROP COLUMN` ไม่มีข้อมูลหาย
- **ค่า default ที่ backfill คือ `cutoffDay` ปัจจุบัน ซึ่งถูกต้อง** เพราะยังไม่เคยมีการ
  เปลี่ยน ทุกแถวที่มีอยู่จึงคำนวณด้วยค่านี้จริง
- การลบรายการเช็คอินเป็น soft-delete — กู้คืนได้ด้วยปุ่มที่มีอยู่
- สลิปที่ `Published`/`Locked` ไม่ถูกแตะ — การเปลี่ยนกติกาช่วงวันมีผลกับการคำนวณ
  ครั้งถัดไปเท่านั้น
- ไม่มีคำสั่งลบหรือเขียนทับข้อมูลเดิมใด ๆ
